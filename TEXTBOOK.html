ЧАСТЬ 1. Базовые понятия

Прежде чем лезть в код, нужно понять 8 вещей. Без них ничего не будет понятно. Не пропускай!

Урок 1. Бэкенд и фронтенд — две половинки сайта

[DOC] Django overview · React: Quick Start

Когда ты открываешь ozon.ru или wildberries.ru, ты видишь красивые кнопки, картинки, анимации. Это фронтенд — программа, которая работает в твоём браузере.

Но когда ты нажимаешь «Купить», браузер отправляет запрос на другой компьютер — сервер. Сервер — это бэкенд. Он:

  • Проверяет, есть ли товар на складе
  • Списывает деньги
  • Сохраняет заказ в базу данных
  • Отправляет email с подтверждением
┌──────────────┐ HTTP ┌──────────────┐ SQL ┌──────────────┐ │ Браузер │ ──────────► │ Сервер │ ────────► │ База данных │ │ (фронтенд) │ ◄────────── │ (бэкенд) │ ◄──────── │ (PostgreSQL) │ │ React │ JSON │ Django │ данные │ Таблицы │ └──────────────┘ └──────────────┘ └──────────────┘
Ресторан. Ты (фронтенд) сидишь за столиком и смотришь в меню. Официант (API) принимает заказ. Кухня (бэкенд) готовит. Склад (база данных) хранит продукты.
Наш проект — это бэкенд. Он НЕ рисует кнопки. Он только получает запросы и отдаёт данные в формате JSON.

Браузер и сервер общаются через протокол HTTP (HyperText Transfer Protocol). Это как язык, на котором они разговаривают.

Есть 4 основных типа запроса:

Урок 3. JSON — язык обмена данными

[DOC] MDN: JSON · json.org

JSON (JavaScript Object Notation) — это формат, в котором бэкенд отдаёт данные фронтенду. Выглядит так:

{
  "id": 1,
  "name": "iPhone 15",
  "price": 89990,
  "in_stock": true,
  "categories": ["Смартфоны", "Электроника"]
}

Это просто текст с парами «ключ: значение». Значения могут быть: число, строка (в кавычках), логическое (true/false), массив (в квадратных скобках), объект (в фигурных).

JSON — это язык, на котором фронтенд и бэкенд разговаривают между собой. Как английский для дипломатов — оба понимают.
Открой в браузере http://localhost:8000/api/v1/health/ — ты увидишь JSON-ответ: {"status": "ok", "version": "1.0.0", "database": "ok"}

Урок 5. База данных — склад информации

[DOC] Django Models

База данных (БД) — это место, где хранятся ВСЕ данные магазина. Пользователи, товары, заказы, корзины — всё в таблицах. Как в Excel, но мощнее:

Таблица "users_user": Таблица "catalog_product": ┌────┬──────────────────┬──────────┐ ┌────┬────────────┬─────────┐ │ id │ email │ username │ │ id │ name │ rating │ ├────┼──────────────────┼──────────┤ ├────┼────────────┼─────────┤ │ 1 │ ivan@example.com │ ivan │ │ 1 │ iPhone 15 │ 4.5 │ │ 2 │ maria@mail.ru │ maria │ │ 2 │ MacBook │ 4.8 │ └────┴──────────────────┴──────────┘ └────┴────────────┴─────────┘

Мы используем PostgreSQL — настоящую профессиональную базу данных. Она умеет:

  • Транзакции — «всё или ничего» (подробнее в уроке 19)
  • Блокировки — защита от одновременных изменений
  • Индексы — ускорение поиска
  • Полнотекстовый поиск — поиск по словам в описаниях
База данных — это склад магазина. Товары на полках, записи в журналах. Когда кассир пробивает товар — он ищет его на складе по штрих-коду (id).

Урок 7. ORM — переводчик Python ↔ SQL

[DOC] Django ORM Queries

ORM (Object-Relational Mapping) — это способ работать с базой данных через Python-объекты, без написания SQL.

Вместо:

SELECT * FROM catalog_product WHERE rating > 4.0 ORDER BY min_price;

Пишешь:

Product.objects.filter(rating__gt=4.0).order_by('min_price')

ORM сам переводит Python-код в SQL и отправляет в базу.

ORM — это переводчик. Ты говоришь по-русски, ORM переводит на SQL (язык базы данных).
Два подчёркивания __ в ORM — это «особый вызов»: __gt = greater than, __lt = less than, __icontains = поиск без учёта регистра.

Урок 8. JWT-токен — электронный паспорт

[DOC] SimpleJWT · jwt.io

Когда ты логинишься, бэкенд выдаёт тебе JWT-токен — длинную строку вроде паспорта:

eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJ1c2VyX2lkIjoxfQ.abc123...

Этот токен фронтенд отправляет с каждым запросом, и бэкенд понимает: «А, это Иван!»

Два токена:

ТокенЖивётЗачем
Access15 минутДля обычных запросов
Refresh7 днейПолучить новый access без повторного логина
JWT — это браслет в аквапарке. Показал на входе — пустили. Потерял — иди на кассу (логинься заново). Действует до конца дня (15 мин). Если просрочился — показываешь специальный талон (refresh) и получаешь новый браслет.
Токен хранится в localStorage в браузере и отправляется в заголовке Authorization: Bearer <токен> с каждым запросом.

Урок 11. Путь запроса — от кнопки до базы и обратно

[DOC] Django Request/Response

Когда фронтенд отправляет POST /api/v1/cart/items/ {variant_id: 5, quantity: 2}:

1. URL: /api/v1/cart/items/ → CartItemView (api_views/) 2. View: Принимает запрос, вызывает сериализатор 3. Serial: Проверяет данные (variant_id есть? quantity > 0?) 4. View: Вызывает CartService.add_item() (services/) 5. Service: @transaction.atomic + select_for_update Проверяет сток, ищет корзину, создаёт CartItem 6. ORM: INSERT INTO cart_cartitem (...) (models/) 7. Service: Возвращает обновлённую корзину 8. View: Отдаёт JSON-ответ (serializers/)
Как в ресторане: официант (URL) принимает заказ → проверяет бланк (Serializer) → передаёт на кухню (Service) → повар готовит по рецепту (бизнес-логика) → берёт продукты из холодильника (ORM → БД) → отдаёт блюдо через официанта (View → JSON).
Главное правило: View НЕ содержит бизнес-логику! View только принимает запрос, валидирует, вызывает сервис, возвращает ответ. Вся «умная» работа — в сервисе.

ЧАСТЬ 3. Модели — таблицы в базе

Урок 12. BaseModel — общий предок

[DOC] Abstract base classes

У нас есть абстрактная модель apps/core/models/base_model.py:

class BaseModel(models.Model):
    created_at = models.DateTimeField(auto_now_add=True)  # Один раз при создании
    updated_at = models.DateTimeField(auto_now=True)      # Каждый раз при save()

    class Meta:
        abstract = True   # Django НЕ создаёт таблицу для BaseModel!

Все модели (кроме User) наследуют BaseModel → получают created_at и updated_at бесплатно.

BaseModel — как заготовка для паспорта. Все паспорта имеют страницу «Дата выдачи» и «Дата замены». Не нужно каждый раз рисовать эти страницы — они уже есть в шаблоне.
abstract = True — критически важно! Без него Django создал бы отдельную таблицу core_basemodel, а все модели ссылались бы на неё через OneToOneField → лишние JOIN'ы → медленные запросы.

Урок 13. Пользователь — модель User

[DOC] Custom User model

Модель User — особенная: она наследует AbstractUser (не BaseModel!):

class User(AbstractUser):
    phone = models.CharField(max_length=20, blank=True, default='')
    email = models.EmailField(unique=True)  # Обязательный, уникальный!

AbstractUser уже даёт: username, email, first_name, last_name, is_active, is_staff, is_superuser, date_joined, password (хэшированный).

Мы переопределили email: в стандартном AbstractUser он blank=True (необязательный), а мы сделали unique=True (обязательный, уникальный).

User НЕ наследует BaseModel → у него НЕТ created_at и updated_at. Зато есть date_joined от AbstractUser.

Урок 14. Товар — модель Product

[DOC] SlugField · django-treebeard

Товар — центральная сущность магазина. Ключевые поля:

class Product(BaseModel):
    uuid = models.UUIDField(default=uuid.uuid4, editable=False)
    slug = models.SlugField(unique=True)
    name = models.CharField(max_length=500)
    description = models.TextField(blank=True)
    status = models.CharField(choices=ProductStatus.choices, default=ProductStatus.DRAFT)
    brand = models.ForeignKey(Brand, on_delete=models.SET_NULL, null=True)
    min_price = models.DecimalField(max_digits=12, decimal_places=2, default=0)
    max_price = models.DecimalField(max_digits=12, decimal_places=2, default=0)
    rating = models.DecimalField(max_digits=3, decimal_places=2, default=0)
    reviews_count = models.PositiveIntegerField(default=0)
    views_count = models.PositiveIntegerField(default=0)

Зачем uuid вместо id? Если показывать id=1, id=2, id=3 — конкурент узнает, сколько у тебя товаров. UUID непредсказуем.

Зачем slug? URL /products/iphone-15/ красивее и лучше для SEO, чем /products/550e8400-e29b/.

Зачем min_price/max_price? Денормализованные цены — чтобы не делать JOIN к Price при каждом показе списка товаров.

Денормализация — когда мы храним копию данных в другой таблице для скорости. Например, min_price в Product — это копия минимальной цены из Price. При изменении цены нужно обновить и Product.min_price (через сигнал).

Урок 15. Корзина — модели Cart и CartItem

[DOC] ForeignKey 
class Cart(BaseModel):
    user = models.ForeignKey(User, on_delete=models.CASCADE, null=True)
    session_key_hash = models.CharField(max_length=64, null=True)
    is_active = models.BooleanField(default=True)

Два типа владельца:

  • Авторизованный: user заполнен, session_key_hash = NULL
  • Гость: user = NULL, session_key_hash = SHA-256 хэш ключа сессии
Почему хэш, а не оригинальный session_key? Если база утечёт — хакер получит хэши, но не сможет подставить их в cookie. SHA-256 необратим!
class CartItem(BaseModel):
    cart = models.ForeignKey(Cart, on_delete=models.CASCADE, related_name='items')
    variant = models.ForeignKey(ProductVariant, on_delete=models.CASCADE)
    quantity = models.PositiveIntegerField(default=1)

Один CartItem = одна позиция в корзине. related_name='items' позволяет писать cart.items.all().

Урок 16. Заказ — модель Order и статусная машина

[DOC] django-fsm

Заказ — одна из самых сложных моделей. Ключевые поля:

class Order(BaseModel):
    status = models.CharField(choices=OrderStatus.choices, default=OrderStatus.PENDING)
    user = models.ForeignKey(User, on_delete=models.PROTECT)
    order_number = models.CharField(max_length=20, unique=True, editable=False)
    subtotal = models.DecimalField(max_digits=12, decimal_places=2)
    delivery_cost = models.DecimalField(max_digits=10, decimal_places=2, default=0)
    discount = models.DecimalField(max_digits=12, decimal_places=2, default=0)
    total = models.DecimalField(max_digits=12, decimal_places=2)

Статусы заказа (FSM — Finite State Machine, конечный автомат):

PENDING (ожидает оплаты) │ ▼ CONFIRMED (подтверждён) ←─── оплата прошла │ ▼ PROCESSING (в обработке) ←─── начали собирать │ ▼ SHIPPED (отправлен) ←─── передали в доставку │ ▼ DELIVERED (доставлен) ←─── клиент получил На любом этапе → CANCELLED (отменён)

Правила переходов зашифрованы в словаре:

ORDER_STATUS_TRANSITIONS = {
    'PENDING':    ['CONFIRMED', 'CANCELLED'],
    'CONFIRMED':  ['PROCESSING', 'CANCELLED'],
    'PROCESSING': ['SHIPPED', 'CANCELLED'],
    'SHIPPED':    ['DELIVERED', 'CANCELLED'],
    'DELIVERED':  [],    # Терминальный — никуда больше
    'CANCELLED':  [],    # Терминальный — никуда больше
}
Нельзя перескочить из PENDING сразу в SHIPPED — сервис не позволит. Это как уровни в игре: нельзя перейти на уровень 3, не пройдя уровень 2.

Адрес — SNAPSHOT (копия), не FK! Когда пользователь меняет адрес в профиле, данные заказа НЕ меняются. Это критично для чеков и возвратов.

DecimalField, не float! 0.1 + 0.2 = 0.30000000000000004 в float. Decimal считает точно до копейки.

Урок 17. ForeignKey, Constraints, Indexes

[DOC] Model Meta options · Constraints

ForeignKey — связь между таблицами

CartItem.cart = models.ForeignKey(Cart, on_delete=models.CASCADE, related_name='items')

Это значит: каждый CartItem привязан к ОДНОЙ корзине, а корзина имеет МНОГО items.

Cart #1 ←── CartItem (iPhone, 2 шт) ←── CartItem (MacBook, 1 шт) Cart #2 ←── CartItem (AirPods, 3 шт)

Constraints — правила в базе

models.UniqueConstraint(
    fields=['user'],
    condition=Q(is_active=True) & Q(user__isnull=False),
    name='unique_active_user_cart',
)

Это правило: у одного пользователя — максимум ОДНА активная корзина. База данных сама это гарантирует.

Indexes — ускорение поиска

models.Index(fields=['user', 'is_active'], name='cart_user_active_idx')

Индекс — как алфавитный указатель в книге. Без него поиск «все активные корзины пользователя» = перелистать ВСЮ книгу (Full Table Scan). С индексом — сразу на нужную страницу.

ЧАСТЬ 4. Сервисы — мозг проекта

Урок 18. Service Layer — зачем выносить логику

[DOC] Cosmic Python · Django transactions

Зачем сервисы отдельным слоем? Представь:

❌ БЕЗ сервисов (логика в View): View сам проверяет сток, создаёт корзину, считает цену, резервирует товар → 200 строк в одном методе → если нужно «создать заказ из CLI» — дублируем код ✅ С СЕРВИСАМИ: View: «CartService, добавь товар» — 3 строки Service: проверяет сток, создаёт корзину, считает цену — всё в одном месте → View, CLI, management-команда используют один сервис
Правило: View → Serializer → Service → ORM. View не знает про транзакции. Serializer не знает про бизнес-логику. Service не знает про HTTP.

Урок 19. transaction.atomic — «Всё или ничего»

[DOC] atomic() 
@transaction.atomic
def transfer_money(from_account, to_account, amount):
    from_account.balance -= amount      # Шаг 1
    from_account.save()
    to_account.balance += amount        # Шаг 2
    to_account.save()
    # Если шаг 2 упал — шаг 1 тоже откатывается автоматически!
transaction.atomic — как эскроу-счёт при покупке квартиры. Или деньги переведены покупателю, или квартира — продавцу. Не бывает «деньги списаны, а квартира не передана».

Урок 20. select_for_update — «Занято, не трогай!»

[DOC] select_for_update() 
stock = Stock.objects.select_for_update().get(variant=variant)
stock.quantity -= 1
stock.save()

Пока мы держим select_for_update(), другой запрос НЕ может изменить эту строку. Это защищает от race condition — когда два человека одновременно покупают последний товар.

БЕЗ select_for_update: Запрос A: stock.quantity = 1 ← видит 1 Запрос B: stock.quantity = 1 ← тоже видит 1 Запрос A: quantity -= 1 → 0 ← сохраняет 0 Запрос B: quantity -= 1 → 0 ← тоже сохраняет 0 Результат: продали 2 товара, а был только 1! ❌ С select_for_update: Запрос A: SELECT FOR UPDATE → quantity = 1 ← ЗАБЛОКИРОВАЛ Запрос B: SELECT FOR UPDATE → ЖДЁТ... Запрос A: quantity -= 1 → 0, COMMIT ← разблокировал Запрос B: SELECT FOR UPDATE → quantity = 0 ← видит 0 Запрос B: ОШИБКА «Недостаточно на складе» ✅

Урок 21. CartService — читаем реальный код

[DOC] F() expressions

Вот как выглядит добавление товара в корзину (упрощённо):

@staticmethod
@transaction.atomic
def add_item(cart, variant_id, quantity=1):
    # Шаг 0: Базовая валидация
    if quantity < 1:
        raise ValidationError('Количество должно быть ≥ 1')

    # Шаг 1: Проверка лимита позиций
    if cart.items.count() >= 100:
        raise ValidationError('Слишком много товаров в корзине')

    # Шаг 2: Загрузка варианта с проверкой активности
    variant = ProductVariant.objects.select_related('product', 'stock')\
        .get(pk=variant_id, is_active=True)

    # Шаг 3: Проверка что ТОВАР тоже активен
    if variant.product.status != 'active':
        raise NotFound('Товар недоступен для заказа.')

    # Шаг 4: select_for_update — блокировка строки
    existing = CartItem.objects.select_for_update()\
        .filter(cart=cart, variant=variant).first()

    # Шаг 5: Проверка остатков на складе
    stock = getattr(variant, 'stock', None)
    if stock and quantity > stock.quantity:
        raise ValidationError('Недостаточно на складе')

    # Шаг 6: Создание или обновление
    if existing:
        existing.quantity += quantity
        existing.save()
    else:
        CartItem.objects.create(cart=cart, variant=variant, quantity=quantity)

    return cart

6 шагов! Каждый — защита от определённой ошибки. Без любого из них — баг:

ШагЧто проверяетЧто будет без него
0quantity ≥ 1Добавят -5 товаров
1Лимит 100 позиций100000 позиций → тормозит
2Вариант активенКупят удалённый товар
3Товар активенКупят черновик
4select_for_updateRace condition — 2 позиции вместо 1
5Остаток на складеПродадят то, чего нет

Урок 22. Сериализатор — переводчик Python ↔ JSON

[DOC] DRF Serializers

Сериализатор делает две вещи:

  1. Вход: проверяет данные из запроса (валидация)
  2. Выход: превращает Python-объект в JSON

Пример входного сериализатора:

class AddToCartInputSerializer(serializers.Serializer):
    variant_id = serializers.IntegerField(min_value=1)    # Обязательное, ≥ 1
    quantity = serializers.IntegerField(min_value=1, default=1)  # Опциональное, по умолчанию 1

Если отправить {"variant_id": "abc"} → ошибка: «variant_id должен быть числом».

Пример выходного сериализатора:

class CartItemSerializer(serializers.ModelSerializer):
    class Meta:
        model = CartItem
        fields = ['id', 'product_name', 'sku', 'price', 'quantity', 'total_price']

Результат:

{
    "id": 5,
    "product_name": "iPhone 15",
    "sku": "IP15-128-BLK",
    "price": "89990.00",
    "quantity": 2,
    "total_price": "179980.00"
}
Сериализатор — таможенник. Проверяет багаж (данные) на входе и упаковывает товар (объект) для отправки на выходе.

Урок 23. View — приёмная запросов

[DOC] DRF APIView

View — это класс, который принимает HTTP-запрос и возвращает HTTP-ответ:

class CartItemView(APIView):
    permission_classes = (AllowAny,)  # Любой может добавить в корзину

    def post(self, request):
        # 1. Валидируем входящие данные
        input_ser = AddToCartInputSerializer(data=request.data)
        input_ser.is_valid(raise_exception=True)

        # 2. Получаем корзину (создаём если нет)
        cart = CartService.get_or_create_cart(request)

        # 3. Вызываем бизнес-логику
        CartService.add_item(
            cart=cart,
            variant_id=input_ser.validated_data['variant_id'],
            quantity=input_ser.validated_data.get('quantity', 1),
        )

        # 4. Возвращаем обновлённую корзину
        return Response(CartSerializer(cart).data, status=201)
View НЕ содержит бизнес-логику. Только 4 шага: принял → валидировал → вызвал сервис → вернул ответ.

ЧАСТЬ 6. Как всё работает вместе

Урок 26. Полный путь покупки

[DOC] django-cors-headers

Вот что происходит, когда пользователь покупает товар:

1. 👤 ПОЛЬЗОВАТЕЛЬ ЗАХОДИТ НА САЙТ → users: Регистрация/Логин → JWT-токен 2. 📦 ПРОСМАТРИВАЕТ КАТАЛОГ → catalog: Список товаров, категории, бренды → analytics: Записываем просмотр (record_view) 3. 🛒 КЛАДЁТ В КОРЗИНУ → cart: CartService.add_item() → inventory: Проверяем остаток (stock.quantity) 4. 📋 ОФОРМЛЯЕТ ЗАКАЗ → orders: OrderService.create_from_cart() → cart: Корзина деактивируется → inventory: Статус CONFIRMED → резервируем товар → discounts: Применяем купон если есть → shipping: Рассчитываем стоимость доставки → notifications: «Ваш заказ создан!» 5. 💳 ОПЛАЧИВАЕТ → payments: PaymentService.process() → orders: Статус CONFIRMED → PROCESSING → notifications: «Оплата прошла!» 6. 🚚 ОТПРАВЛЯЕТСЯ → shipping: Shipment → IN_TRANSIT → orders: Статус PROCESSING → SHIPPED → notifications: «Заказ отправлен!» 7. 📦 ДОСТАВЛЯЕТСЯ → shipping: Shipment → DELIVERED → orders: Статус SHIPPED → DELIVERED → inventory: Списываем со склада (commit) → notifications: «Заказ доставлен!» 8. ⭐ ОСТАВЛЯЕТ ОТЗЫВ → reviews: ReviewService.create() → catalog: Пересчитываем рейтинг товара

Урок 27. Статусная машина заказа (подробнее)

[DOC] django-fsm

Статусная машина гарантирует, что заказ проходит через статусы по правилам. Сервис OrderService.transition_status() проверяет:

def transition_status(order, new_status):
    allowed = ORDER_STATUS_TRANSITIONS.get(order.status, [])
    if new_status not in allowed:
        raise ValidationError(
            f'Нельзя перейти из {order.status} в {new_status}'
        )
    order.status = new_status
    order.save()

Это защищает от багов: никто не сможет «перепрыгнуть» статус или вернуть доставленный заказ обратно в обработку.

Урок 28. Сигналы — автодействия

[DOC] Django Signals

Сигнал — автоматическое действие при каком-то событии. Django сообщает: «Произошло X!» — и твой код реагирует.

Пример: при создании пользователя автоматически создаём профиль:

@receiver(post_save, sender=User)
def create_user_profile(sender, instance, created, **kwargs):
    if created:
        UserProfile.objects.create(user=instance)

Пример: при создании отзыва пересчитываем рейтинг товара:

@receiver(post_save, sender=Review)
def recalculate_product_rating(sender, instance, **kwargs):
    product = instance.product
    reviews = Review.objects.filter(product=product, is_approved=True)
    product.rating = reviews.aggregate(avg=Avg('rating'))['avg'] or 0
    product.reviews_count = reviews.count()
    product.save()
Сигнал — как датчик дыма. Сработал → автоматически вызвал пожарных. Ты не звонишь сам — система реагирует сама.

Урок 29. Слияние корзин — когда гость логинится

[DOC] Session framework

Гость наполнил корзину. Потом залогинился. Что делать с гостевой корзиной? Слить её в пользовательскую!

Гостевая корзина: Пользовательская корзина: iPhone 15 × 2 MacBook × 1 AirPods × 1 РЕЗУЛЬТАТ СЛИЯНИЯ: iPhone 15 × 2 ← из гостевой MacBook × 1 ← было AirPods × 1 ← из гостевой

Алгоритм CartService.merge_guest_into_user_cart():

  1. Найти гостевую корзину по session_key_hash
  2. Получить/создать корзину пользователя
  3. Для каждой позиции гостевой корзины:
    • Проверить variant.is_active → пропустить неактивные
    • Если позиция уже есть в юзерской → сложить quantity
    • Иначе → создать новую позицию
    • Ограничить quantity доступным остатком (stock)
  4. Деактивировать гостевую корзину (НЕ удалять!)
Гостевую корзину мы ДЕАКТИВИРУЕМ, а не удаляем — для аналитики (сколько корзин было слито) и восстановления.

class CartServiceTests(TestCase):
    def test_add_item(self):

Урок 31. Миграции — эволюция базы данных

[DOC] Django Migrations

Миграция — это инструкция «как изменить базу данных». Как коммиты в Git, но для структуры таблиц.

# 0001_initial.py — создаёт таблицу
operations = [
    migrations.CreateModel(
        name='Cart',
        fields=[
            ('id', models.BigAutoField(primary_key=True)),
            ('user', models.ForeignKey(...)),
            ('is_active', models.BooleanField(default=True)),
        ],
    ),
]

Команды:

python manage.py makemigrations  # Модель → SQL (создать миграцию)
python manage.py migrate         # Выполнить SQL (применить миграцию)
Миграции — как строительные чертежи. Сначала «Фундамент» (0001), потом «Стены» (0002), потом «Крыша» (0003). Нельзя построить крышу без стен!
Никогда не удаляй миграции, которые уже применены на сервере! Это как сжечь чертежи, когда дом уже построен. Если нужно откатить — используй python manage.py migrate app_name migration_number.
